AI-NATIVE NO-CODE APPLICATION & WORKFLOW BUILDER

Product Context, Vision, Scope, Architecture, UX, MVP and Implementation Brief

Document purpose: This document is the primary product and engineering
context for building the project with Claude Code. It describes what the
product is, what problem it solves, how it should behave, what the user
experience should look like, what the core architecture should be, what
should and should not be built in the MVP, and what a realistic
end-to-end deployed version should accomplish.

IMPORTANT: This is NOT a plan to build another Lovable, Bolt, v0,
Replit, or generic AI website/code generator. The product should be
intentionally constrained and architecture-driven so that one developer
can build and deploy it.

====================================================================== 1.
PRODUCT IDEA
======================================================================

Working description:

An AI-native no-code platform where a user describes a small business
application or operational process in natural language, and the platform
converts that description into a runnable application composed from a
controlled set of reusable primitives.

The platform should generate:

1.  Application structure
2.  Pages and UI
3.  Forms and tables
4.  Database entities
5.  Users and roles
6.  Permissions
7.  Business rules
8.  Workflows
9.  AI actions/agents where useful
10. Notifications
11. Workflow execution and logs
12. A live preview
13. A publishable/shareable URL

The key architectural idea is:

THE LLM DOES NOT DIRECTLY GENERATE AND DEPLOY AN ARBITRARY CODEBASE.

Instead:

Natural-language requirement -> AI planner -> Structured Application
Specification -> Structured Workflow Specification -> Validation ->
Deterministic runtime -> Runnable application

This is critical.

The product is a “Lego” application builder, not an unrestricted code
generator.

The AI chooses and configures a finite set of supported primitives. The
platform runtime renders those primitives and executes the resulting
workflows.

======================================================================
2. THE PROBLEM
======================================================================

Small businesses, freelancers, student organizations, agencies, and
non-technical teams often know exactly what process they want to
digitize but do not know how to build software for it.

For example:

“I run a small company. Employees should submit leave requests. Managers
should approve or reject them. Employees should see their history.
Managers should receive notifications.”

Today, a person may need to understand:

-   frontend development
-   backend development
-   databases
-   authentication
-   role-based access
-   APIs
-   workflow automation
-   notifications
-   deployment
-   hosting
-   DNS
-   integrations

Traditional no-code tools reduce some of the programming burden, but
users may still need to manually design the application and workflow.

AI code/app builders reduce the coding burden, but they commonly operate
around generating an application/codebase rather than giving a simple
business user a constrained, predictable application runtime and
workflow engine.

The opportunity:

A user should be able to describe WHAT they want their small business
system to do without having to understand HOW it should be implemented.

5. PRIMARY EXAMPLE: EMPLOYEE LEAVE MANAGEMENT
======================================================================

This should be one of the main demo applications.

User prompt:

“I want an employee leave management system. Employees should log in and
request leave. Managers should be able to see pending requests and
approve or reject them. Employees should see their leave history. When a
request is approved or rejected, the employee should be notified.”

The AI should understand this as:

APPLICATION: Employee Leave Management

USERS: - Employee - Manager

PAGES: - Login - Employee Dashboard - Request Leave - Leave History -
Manager Dashboard - Pending Approvals

DATABASE ENTITIES: - Users - Leave Requests - Leave Balances

WORKFLOW: Employee submits request -> Create leave request -> Notify
manager -> Wait for manager decision -> IF approved: update request
status update leave balance notify employee IF rejected: update request
status notify employee

PERMISSIONS: Employee: - create leave request - view own requests - view
own balance - cannot approve requests

Manager: - view team requests - approve/reject requests - cannot modify
unrelated application data

The result should be a real, functioning application, not a mockup.

======================================================================
10. WORKFLOW ORCHESTRATION
======================================================================

Workflow orchestration is the execution system behind the generated
applications.

A workflow is a graph of nodes.

Example:

[Form Submitted] | v [Create Record] | v [AI Classify] | v [Condition] /
/
High Normal | | v v [Notify] [Assign] | | +—-+—–+ | v [Complete]

The orchestrator is responsible for:

-   determining execution order
-   passing data between nodes
-   evaluating conditions
-   invoking actions
-   calling AI actions
-   handling errors
-   retrying where appropriate
-   waiting for human approvals
-   recording execution history
-   stopping failed workflows safely

Important: Do not over-engineer this into a distributed workflow
platform for the MVP.

A database-backed workflow engine with deterministic execution is
sufficient.

======================================================================
11. AI VS DETERMINISTIC EXECUTION
======================================================================

This distinction is fundamental.

Use AI for:

-   interpreting natural-language requirements
-   generating application specifications
-   generating workflow specifications
-   classifying text
-   extracting structured information
-   summarization
-   deciding between explicitly permitted AI actions

Use deterministic code for:

-   authentication
-   authorization
-   database CRUD
-   conditions
-   workflow state
-   record updates
-   notifications where possible
-   retries
-   execution logs
-   application routing

Do NOT let an LLM arbitrarily execute database queries or sensitive
actions.

The LLM should produce structured, validated instructions.

======================================================================
12. WORKFLOW SPECIFICATION
======================================================================

The AI should produce a strict structured representation.

Conceptual example:

workflow: name: Leave Approval

trigger: type: form_submission source: leave_request

nodes: - id: create_request type: database.create entity: leave_requests

    - id: notify_manager
      type: notification
      channel: in_app

    - id: manager_approval
      type: approval
      role: manager

    - id: update_status
      type: database.update

    - id: notify_employee
      type: notification
      channel: in_app

edges: create_request -> notify_manager notify_manager ->
manager_approval manager_approval -> update_status update_status ->
notify_employee

This is illustrative only. Use a proper validated schema in
implementation.

The system should validate:

-   node types
-   required properties
-   allowed transitions
-   referenced entities
-   referenced roles
-   permissions
-   data types

======================================================================
19. PUBLISHING MODEL
======================================================================

CRITICAL ARCHITECTURAL DECISION:

Do NOT deploy a brand-new server/application infrastructure for every
generated app in the MVP.

All generated applications should run on the same platform runtime.

Conceptually:

                 YOUR PLATFORM
                      |
        +-------------+-------------+
        |             |             |
      App A         App B         App C
     tenant=1      tenant=2      tenant=3
        |             |             |
        +-------------+-------------+
                      |
               Shared Runtime
                      |
                 PostgreSQL

An application is primarily configuration/data interpreted by the
runtime.

Publishing means:

application.status = “published”

The platform then exposes a URL such as:

https://app.yourplatform.com/a/8f72k

The route identifies the application.

The runtime loads the corresponding application configuration and
renders it.

No GitHub, Vercel, DNS, or custom server setup should be required for
the normal user.

======================================================================
22. MULTI-TENANCY
======================================================================

This is one of the most important backend concepts.

Applications must be isolated.

Example:

Application A: application_id = 101

Application B: application_id = 102

All generated data must be associated with the correct application.

Example:

leave_requests: - id - application_id - employee_id - start_date -
end_date - status

Every database access must enforce application ownership/tenant
boundaries.

Do not rely only on frontend filtering.

Authorization must be enforced server-side.

If using Postgres/Supabase, investigate Row Level Security.

26. AI SAFETY / RELIABILITY
======================================================================

The LLM should never be trusted as the source of truth for security.

Never allow:

-   arbitrary SQL from the model
-   arbitrary server-side code execution
-   unrestricted shell execution
-   arbitrary API calls
-   unrestricted credential access

Use allowlisted actions.

For example:

ALLOWED ACTION TYPES:

database.create database.update database.query notification.in_app
notification.email workflow.approval workflow.condition ai.classify
ai.extract webhook.call

Each action should have a defined input/output schema.

38. DEVELOPMENT ORDER
======================================================================

Do NOT start by building the AI.

First prove the runtime.

Recommended order:

1.  Manually define an application JSON/configuration.
2.  Render it.
3.  Connect it to database.
4.  Implement auth.
5.  Implement roles.
6.  Implement workflow engine.
7.  Execute workflows.
8.  Add logs.
9.  Build visual workflow display.
10. Only then add LLM generation.

Reason:

If the runtime does not work, AI-generated configuration will not save
the project.

The AI should sit on top of a functioning deterministic system.

40. CLAUDE CODE DEVELOPMENT INSTRUCTIONS
======================================================================

When implementing this project:

1.  Do not over-engineer.
2.  Prefer simple, explicit architecture.
3.  Keep the application specification strongly typed.
4.  Validate all LLM output.
5.  Never trust raw LLM output.
6.  Keep workflow execution deterministic.
7.  Keep tenant isolation server-side.
8.  Separate platform users from generated-app users.
9.  Make every workflow execution observable.
10. Write tests for workflow execution.
11. Keep AI provider abstraction replaceable.
12. Keep deployment inexpensive.
13. Avoid unnecessary dependencies.
14. Build incrementally.
15. Keep the generated application runtime independent from the AI
    planner.

When a feature can be implemented deterministically, do not use an LLM
for it.

Working product definition:

An AI-native no-code platform for creating small business and internal
applications from natural-language requirements.

Core promise:

“Describe your process. Build the application. Run the workflow. Share
the system.”

Core architecture:

Natural Language -> AI Planner -> Application Specification + Workflow
Specification -> Validation -> Runtime -> Database + Auth + Workflow
Engine -> Live Application -> Execution Logs -> Publishable URL

Core innovation:

A controlled, configuration-driven application runtime combined with
AI-generated executable workflows.

The system should prioritize a small number of powerful primitives over
unlimited code generation.

The ultimate goal is NOT to build a competitor to Lovable.

The goal is to build a small, technically rigorous, useful product that
makes it possible for a non-technical user to describe a repetitive
business process and receive a working application that actually
executes that process.
